# Architecture

## Stack rationale

- **FastAPI + Pydantic**: async-capable, strong request/response validation
  for free, auto-generated OpenAPI docs the frontend and any future client
  can rely on.
- **SQLAlchemy 2.x + Alembic**: typed ORM models, reviewable migrations
  instead of hand-run DDL. The initial migration in this repo was
  autogenerated from the models and verified by actually applying it and
  listing the resulting tables (see `README.md`).
- **PostgreSQL** for production, **SQLite** for local dev and the test
  suite — the code path is identical; only `DATABASE_URL` changes. JSON and
  Enum columns are used in a way that's portable across both.
- **React + TypeScript + Vite + Tailwind v4**: fast iteration, typed API
  contracts shared via `src/api/types.ts`, no CSS build step beyond Vite's
  own plugin.
- **Argon2id** (via passlib): the current OWASP-recommended password
  hashing algorithm. No legacy hash scheme exists in this codebase to fall
  back to.

## Service boundaries

The backend is a single FastAPI app today (not yet split into separate
deployable services), but internally organized so that split is
straightforward later:

- `app/core/` — identity and request-level security primitives (hashing,
  JWT, RBAC dependency, rate limiting). Every other module depends on this;
  this module depends on nothing else in the app.
- `app/services/` — pure(ish) business logic with no FastAPI imports:
  `url_analysis.py`, `message_analysis.py`, `password_strength.py`,
  `breach_provider.py`, `security_score.py`, `ssrf_guard.py`. These are
  unit-tested directly, independent of the HTTP layer.
- `app/api/routes/` — one router per module, translating HTTP requests into
  calls against `services/` and `models/`. Route handlers never contain
  scoring or analysis logic themselves.
- `app/models/` — one SQLAlchemy model per table, one file per model.

This mirrors the "Account Security / Threat Engine / AI Engine →
Security Engine → Alerts/Reports/Analytics" shape from the original
concept brief, just expressed as Python modules rather than separate
network services — appropriate for an MVP's scale, and a clean seam to
split along later if load requires it.

## Data flow: a URL check

1. Frontend `UrlChecker.tsx` calls `POST /api/v1/url-checker/check` (works
   for both anonymous and logged-in visitors).
2. `api/routes/url_checker.py` validates the request shape (Pydantic), then
   calls `services/url_analysis.analyze_url()`.
3. `url_analysis.py` runs structural checks immediately, then calls
   `services/ssrf_guard.validate_url_is_safe_to_fetch()` **before any
   network request**, resolving the hostname and rejecting private/
   loopback/metadata addresses. The same guard runs again on every
   redirect hop.
4. The result (score + indicator list) is persisted to `UrlCheck` and, for
   logged-in users scoring "high", published to `Alert`.
5. The response is never fabricated: any check the pipeline could not
   actually perform (e.g. no reputation provider configured) is marked
   `"not_evaluated": true` rather than silently assumed safe.

## Score engine

`services/security_score.py` computes a 0–100 score from only the signals
the platform can currently verify for that user (MFA status, email
verification, latest breach check, recent high-risk findings, account
standing). A brand-new user with zero activity gets a defined, non-zero,
explainable score rather than an error or a fabricated "100". Every point
is attributed to a named reason, which the dashboard renders directly —
this is what "documented scoring methodology" means in practice, not just
for the URL checker but for the whole platform.

## Known architectural debt (intentional, documented)

- `datetime.utcnow()` is used throughout instead of timezone-aware
  `datetime.now(timezone.utc)`. This produces deprecation warnings on
  current Python but is not a functional bug (all comparisons are
  consistently naive). Flagged here rather than silently left for someone
  to discover — switching requires auditing every comparison against
  stored (naive) datetimes at the same time, which was out of scope for
  this pass.
- The backend is one deployable unit, not yet split into the separate
  services implied by the original architecture diagram. See
  `docs/ROADMAP.md`.
